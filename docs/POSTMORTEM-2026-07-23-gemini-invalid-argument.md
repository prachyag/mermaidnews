# Post-Mortem: AI วิเคราะห์ข่าวล่มทั้งระบบ (400 INVALID_ARGUMENT)

| | |
|---|---|
| **วันที่เกิดเหตุ** | 23 กรกฎาคม 2569 (ตรวจพบ) — สาเหตุเกิดขึ้นก่อนหน้านั้นโดยไม่มีใครรู้ |
| **สถานะ** | ปิดเคสแล้ว — แก้และยืนยันด้วย API จริง 23 ก.ค. 2569 |
| **ความรุนแรง** | **สูง** — ฟีเจอร์หลัก (เฟส 2: AI คัดกรอง + ร่างแคปชัน) ใช้งานไม่ได้ **100%** ทุกคำขอล้มเหลวพร้อมกัน |
| **ผลกระทบต่อข้อมูล** | ไม่มี — ข่าวคงสถานะ `fetched` ตามการออกแบบ ไม่มีข้อมูลสูญหาย กดประมวลผลซ้ำได้ |
| **การตรวจพบ** | ผู้ใช้รายงานเองหลัง deploy ขึ้น Vercel (ไม่มีระบบแจ้งเตือน) |
| **สาเหตุ** | Dependency ภายนอกเปลี่ยนพฤติกรรมเงียบ ๆ — ไม่ใช่โค้ดที่เราเพิ่งแก้ |

---

## 1. สรุปเหตุการณ์ (Incident Summary)

หลัง deploy ขึ้น Vercel สำเร็จ ผู้ใช้กดให้ AI วิเคราะห์ข่าว แล้วได้ error ทันที:

```json
{"error":{"code":400,"message":"Request contains an invalid argument.","status":"INVALID_ARGUMENT"}}
```

อาการชวนให้เข้าใจผิดอย่างยิ่งว่า **"เพิ่ง deploy แล้วพัง = ปัญหาของ Vercel/environment"** เพราะก่อนหน้านี้ระบบเคยทำงานได้ดีบนเครื่อง dev (วัดผลไว้เองว่า 10 ข่าว/1 request/4.8 วินาที)

ความจริงคือ **โค้ดชุดเดียวกันนี้พังบนเครื่อง dev ด้วย** — เราแค่ไม่ได้เรียก AI อีกเลยตั้งแต่ Google ขยับโมเดล การ deploy จึงเป็นแค่จังหวะที่ทำให้ปัญหาถูกเปิดเผย ไม่ใช่สาเหตุ

---

## 2. สาเหตุที่แท้จริง (Root Cause)

### สาเหตุหลัก — `thinkingBudget: 0` กลายเป็นค่าต้องห้ามเมื่อ alias ขยับรุ่น

โค้ดฮาร์ดโค้ดค่านี้ไว้:

```ts
const MODEL = process.env.GEMINI_MODEL || "gemini-flash-latest";
const GENERATION_CONFIG = {
  thinkingConfig: { thinkingBudget: 0 },  // ← ต้นเหตุ
  maxOutputTokens: 8192,
};
```

`thinkingBudget: 0` = "ปิดโหมดคิดก่อนตอบสนิท" ซึ่ง**เคยใช้ได้จริง**และเป็นการแก้ที่ถูกต้องตอนนั้น (เคยวัดได้ว่าลดเวลาจาก 124 วินาที เหลือ 4.6 วินาที)

แต่ `gemini-flash-latest` เป็น **alias ที่ Google ขยับปลายทางได้ตลอดเวลาโดยไม่แจ้ง** และรุ่นใหม่ที่ alias ชี้ไป (ตอนตรวจสอบพบว่ามี Gemini 3.x ในรายการโมเดลแล้ว) **ไม่อนุญาตให้ปิด thinking สนิท** ค่า `0` จึงกลายเป็น invalid argument

ผลคือ **ทุก request พังพร้อมกัน 100%** ไม่ใช่พังบางข่าว เพราะเป็นค่าคงที่ที่ส่งไปทุกคำขอ

หลักฐานจากการยิง API จริง แยกทีละตัวแปรบนโมเดลเดียวกัน:

| config บน `gemini-flash-latest` | ผล |
|---|---|
| ไม่มี `thinkingConfig` | ✅ OK (แต่ใช้ thinking 592 tokens) |
| **`thinkingBudget: 0`** | ❌ **400 INVALID_ARGUMENT** |
| `thinkingBudget: 128` | ✅ OK — และ `thoughts=0` |
| `thinkingBudget: -1` (dynamic) | ✅ OK (แต่ใช้ thinking 812 tokens) |

ข้อค้นพบสำคัญ: **`budget=128` ให้ `thoughts=0`** คือได้ผลลัพธ์เท่ากับที่เราต้องการตอนตั้ง `0` ทุกประการ แต่ API ยอมรับ ขณะที่การ "ไม่ตั้ง `thinkingConfig` เลย" กลับแพงกว่า (ใช้ thinking จริง 592 tokens)

### สาเหตุซ้อนชั้นที่ 2 — thinking token กิน `maxOutputTokens` ก้อนเดียวกับคำตอบ

**ถ้าแก้แค่ `thinkingBudget` จะยังพังต่อบนโปรดักชัน** — และเกือบเป็นเช่นนั้นจริง

`maxOutputTokens: 8192` เดิมเพียงพอ เพราะตอนปิด thinking โควตาทั้งก้อนเป็นเนื้อคำตอบล้วน พอรุ่นใหม่บังคับให้มี thinking โควตาเดียวกันถูกแบ่งไปให้การคิดก่อน เหลือให้เขียนคำตอบไม่พอ

อาการที่ตามมาเป็นคนละหน้าตากับ error เดิม และ**ร้ายกว่าเพราะบางแบบไม่ throw**:

- `finishReason: MAX_TOKENS` → JSON ถูกตัดกลางคัน
- ได้ `relevant: true` แต่ `caption`/`summary` เป็น `null` — **ข่าวผ่านการคัดกรองแต่ไม่มีเนื้อหาให้โพส โดยระบบไม่ฟ้อง error ใด ๆ**
- ชุด 10 ข่าว บางรอบคืนผลกลับมาแค่ 1 ชิ้น

วัดผลยืนยัน (ชุด 5 ข่าว, prompt จริง):

| `maxOutputTokens` | thinking | สำเร็จ | เวลาเฉลี่ย |
|---|---|---|---|
| 8192 | `budget=-1` | 2/4 | 21.2 วินาที |
| 8192 | `budget=128` | มี MAX_TOKENS + แคปชันหาย | – |
| **32768** | **`budget=128`** | **4/4 (ผลครบ 20/20)** | **4.1 วินาที** |

### สาเหตุร่วมที่ 3 — ขนาดชุดที่เคยเหมาะ ไม่เหมาะอีกต่อไป

`GEMINI_BATCH_SIZE = 10` ถูกเลือกและวัดผลไว้ตอนที่ยังปิด thinking ได้ พอ thinking ถูกบังคับเปิด สมดุลเปลี่ยน — วัดใหม่ได้ว่าชุด 10 ไม่เสถียร (บางรอบคืน 1/10) และช้า 15–30 วินาที ขณะที่ชุด 5 ครบทุกรอบที่ ~4 วินาที

### สาเหตุเชิงระบบ — พึ่ง alias ที่ขยับได้ โดยไม่มีทางถอยและไม่มีใครเฝ้า

รากที่ลึกกว่าค่า config คือ **สถาปัตยกรรมไม่ได้เผื่อว่า dependency ภายนอกจะเปลี่ยนพฤติกรรม**:

1. **ใช้ alias `-latest`** = ยอมให้ Google เปลี่ยนโมเดลใต้เท้าเราเมื่อไหร่ก็ได้ (แลกกับการไม่ต้องตามอัปเดตเอง)
2. **ไม่มีทางถอย** — config ผิดหนึ่งค่า = ล่มทั้งฟีเจอร์ ไม่มีการลองแบบอื่น
3. **ไม่มีใครเฝ้า** — ไม่มี health check หรือ smoke test ที่ยิง AI จริงเป็นระยะ ระบบพังเงียบจนผู้ใช้มาเจอเอง
4. **เทสไม่จับ** — เทสทั้ง 221 ตัว mock AI provider ไว้หมด (ตามที่ตั้งใจ เพื่อไม่ให้เทสพึ่งเน็ต/เสียโควตา) จึงผ่านฉลุยขณะที่ของจริงพัง 100%

**นี่เป็นครั้งที่สองที่ dependency ภายนอกขยับแล้วเราพัง** ครั้งแรกคือ Google News เปลี่ยนรูปแบบ token จนวิธีแกะลิงก์แบบ base64 ตายไป — รูปแบบความล้มเหลวซ้ำเดิม

## 3. การแก้ไขและการยืนยัน (Resolution)

### สิ่งที่แก้

| # | การแก้ | เหตุผล |
|---|---|---|
| 1 | `thinkingBudget: 0` → `128` (env `GEMINI_THINKING_BUDGET`) | ค่าที่ API รับ และให้ `thoughts=0` เท่าเดิม |
| 2 | `maxOutputTokens: 8192` → `32768` (env `GEMINI_MAX_OUTPUT_TOKENS`) | ต้องกว้างพอสำหรับ "คิด + ตอบ" รวมกัน |
| 3 | `GEMINI_BATCH_SIZE` default `10` → `5` | วัดแล้วว่าเสถียรและเร็วกว่าอย่างมีนัยสำคัญ |
| 4 | เจอ `INVALID_ARGUMENT` → จำไว้แล้วยิงใหม่โดยตัด `thinkingConfig` | ครั้งหน้าที่ alias ขยับ ระบบจะ**ช้าลง แทนที่จะล่ม** |
| 5 | retry เมื่อ "ตอบกลับว่าง" (3 ครั้ง, หน่วงเพิ่มขึ้น) | อาการชั่วคราวที่เดิมทำให้**ทั้งชุด**ล้มเหลว (วัดได้ ~2/5 ครั้ง) |

จงใจ **ไม่ retry เมื่อเจอ `MAX_TOKENS`** เพราะเป็นปัญหาเชิงตั้งค่า ลองกี่ครั้งก็ได้ผลเดิม — เปลืองโควตาเปล่า

### การยืนยัน

ยิง API จริงผ่านโค้ดโปรดักชัน (ไม่ใช่ mock):

- ชุด 5 ข่าว × 4 รอบ → **สำเร็จ 4/4, ได้ผลครบ 20/20, แคปชันครบ 11/12, เฉลี่ย 4.1 วินาที**
- คัดข่าวที่ไม่เกี่ยวข้อง (ราคาทอง/หุ้น/พยากรณ์อากาศ) ออกได้ถูกต้องทุกรอบ
- เทส 221 ตัวผ่าน, `tsc` ผ่าน, lint สะอาด, production build ผ่าน

**ไม่ต้องแก้ env บน Vercel** — ค่า default ใหม่ถูกต้องทั้งหมด redeploy อย่างเดียวพอ

## 4. สิ่งที่ทำเพื่อไม่ให้เกิดซ้ำ (Preventative Action Items)

### ✅ ทำเสร็จแล้ว

1. **ทางถอยอัตโนมัติเมื่อ config ถูกปฏิเสธ** — ระบบเสื่อมสภาพอย่างนุ่มนวล (degrade) แทนล่ม
2. **retry อาการชั่วคราว** — "ตอบกลับว่าง" ไม่ทำให้ทั้งชุดตายอีก
3. **ย้ายค่าคงที่ที่เปราะไปเป็น env** — `GEMINI_THINKING_BUDGET`, `GEMINI_MAX_OUTPUT_TOKENS` แก้ได้โดยไม่ต้อง deploy โค้ดใหม่
4. **เขียนคำเตือนไว้ในโค้ดและ `.env.example`** ว่าห้ามตั้ง `thinkingBudget: 0` พร้อมเหตุผล — กันคนในอนาคต (รวมถึงตัวเราเอง) ย้อนกลับไปใช้ค่าที่เคยดูดีกว่า
5. **ตัดการผูกเทสกับค่า default** — เทส batching ระบุ `batchSize` เองแล้ว การจูนค่าไม่ทำให้เทสพังอีก

### ⬜ ยังไม่ได้ทำ (เรียงตามความสำคัญ)

1. **Smoke test ที่ยิง AI จริง** — เทสที่รันแยก (ไม่ใช่ใน CI ปกติ) ยิง Gemini จริง 1 คำขอเล็ก ๆ เพื่อจับกรณี "mock ผ่านแต่ของจริงพัง" ซึ่งเป็นช่องที่ทำให้เคสนี้หลุดมาถึงผู้ใช้
2. **Health check + แจ้งเตือน** — endpoint ที่ตรวจว่า AI ยังเรียกได้ และแจ้งเมื่อล้มเหลวติดกัน แทนที่จะรอผู้ใช้มาบอก
3. **ตัดสินใจเรื่องปักหมุดเวอร์ชันโมเดล** — เลือกระหว่าง:
   - `-latest` (ปัจจุบัน): ได้รุ่นใหม่ฟรี แต่พังได้ทุกเมื่อ — ยอมรับได้ก็ต่อเมื่อมีข้อ 1 และ 2
   - ปักหมุด เช่น `gemini-2.5-flash`: เสถียรกว่ามาก แต่ต้องตามอัปเดตเองก่อนรุ่นถูกปลด
4. **แสดง error ของ AI บน Dashboard ให้ผู้ใช้เห็น** — ตอนนี้ผู้ใช้เห็นแต่ JSON ดิบของ Google ซึ่งไม่บอกว่าต้องทำอะไรต่อ
5. **บันทึกสถิติการเรียก AI** (สำเร็จ/ล้มเหลว/เวลา) เพื่อให้เห็นแนวโน้มเสื่อมก่อนพังสนิท

### 📌 ความรู้ที่ต้องไม่ลืม

- **`thinkingBudget: 0` = 400 บนรุ่นปัจจุบัน** ใช้ `128` แทน (ให้ `thoughts=0` เหมือนกัน)
- **thinking token นับรวมใน `maxOutputTokens`** — ตั้งเพดานต่ำไปจะเจอ JSON ถูกตัด หรือ **`relevant: true` แต่ไม่มีแคปชัน โดยไม่มี error** (อาการนี้อันตรายเพราะเงียบ)
- **การ "ไม่ตั้ง `thinkingConfig`" ไม่เท่ากับ "ปิด thinking"** — กลับใช้ thinking มากกว่าตั้งค่าน้อย ๆ ด้วยซ้ำ
- **ค่าที่จูนไว้มีวันหมดอายุ** เมื่อผูกกับ alias ที่ขยับได้ — `batchSize: 10` ที่เคยวัดว่าดีที่สุด กลายเป็นค่าที่แย่ลงเมื่อโมเดลเปลี่ยน
- **"เพิ่ง deploy แล้วพัง" ไม่ได้แปลว่า deploy คือสาเหตุ** — ต้องพิสูจน์โดยรันโค้ดชุดเดียวกันบน dev ก่อนเสมอ

## 5. สิ่งที่ทำได้ดี

- **ไม่หลงกับดัก "พังหลัง deploy = ปัญหา Vercel"** — เลือกพิสูจน์ด้วยการยิง API จริงจาก local ก่อน ทำให้พบภายในรอบเดียวว่าไม่เกี่ยวกับ Vercel เลย ถ้าเริ่มจากไล่แก้ env/build บน Vercel จะเสียเวลาไปมากโดยไม่เจออะไร
- **แยกตัวแปรทีละตัวก่อนแก้** — ทดสอบ `budget` 4 ค่าบนโมเดลเดียวกัน ทำให้รู้ว่า `128` ให้ `thoughts=0` ซึ่งเป็นข้อมูลที่ทำให้เลือกค่าได้อย่างมีเหตุผล แทนที่จะสุ่มค่าที่ "ไม่ error"
- **ไม่หยุดที่ error หายไป** — หลังแก้ `thinkingBudget` แล้วยังทดสอบต่อจนเจอบั๊กชั้นที่สอง (`maxOutputTokens`) ซึ่งถ้าปล่อยไว้จะไปโผล่บนโปรดักชันในรูปแบบ "ข่าวไม่มีแคปชัน" ที่เงียบและหายากกว่าเดิมมาก
- **วัดผลก่อนและหลังด้วยตัวเลขจริง** ทุกการตัดสินใจ (batch size, budget, token ceiling) มาจากการวัด ไม่ใช่ความรู้สึก
- **ข้อมูลไม่เสียหาย** — การออกแบบเดิมที่ให้ข่าวคงสถานะ `fetched` เมื่อ AI ล้มเหลว (FR-3.4) ทำงานตามที่ตั้งใจ ผู้ใช้กดประมวลผลซ้ำได้ทันทีหลังแก้ ไม่ต้องดึงข่าวใหม่
