# Post-Mortem: โพสลง Facebook Page ไม่สำเร็จ (code 100 → code 200)

| | |
|---|---|
| **วันที่เกิดเหตุ** | 16–17 กรกฎาคม 2569 |
| **สถานะ** | ปิดเคสแล้ว — ผู้ใช้โพสจริงสำเร็จ 17 ก.ค. 2569 |
| **ความรุนแรง** | กลาง — ฟีเจอร์หลัก (เฟส 4) ใช้งานไม่ได้เลยสำหรับผู้ใช้ทั้งหมดของระบบ (1 คน) |
| **ผลกระทบต่อข้อมูล** | ไม่มี — ไม่มีข้อมูลสูญหาย ไม่มีโพสต์ผิดพลาดขึ้นเพจ |
| **การตรวจพบ** | ผู้ใช้รายงานเอง (ไม่มีระบบแจ้งเตือน) |
| **เวลาที่เสียไป** | ~2 รอบการวินิจฉัย โดย 1 รอบเสียไปกับข้อสรุปที่ผิดของผู้วินิจฉัย |

---

## 1. สรุปเหตุการณ์ (Incident Summary)

หลังเฟส 4 (การโพสผ่าน Facebook Graph API) เขียนเสร็จและผ่านการทดสอบด้วย token ปลอม ผู้ใช้กรอกค่า Facebook Page ID และ Page Access Token จริงลงในหน้าจัดการหัวข้อ แล้วกดโพส — ล้มเหลวทันทีด้วย **error code 100**

```
Unsupported post request. Object with ID '898070703351838' does not exist,
cannot be loaded due to missing permissions, or does not support this operation.
```

หลังจากแก้ Page ID เป็นค่าใหม่ error เปลี่ยนเป็น **code 200**

```
(#200) If posting to a page, requires both pages_read_engagement and
pages_manage_posts as an admin with sufficient administrative permission
```

ทั้งสอง error เกิดจาก **การตั้งค่าผิด 2 จุดที่ซ้อนกันอยู่** ไม่ใช่บั๊กในโค้ด — แต่ระบบไม่มีอะไรช่วยผู้ใช้แยกแยะเลย และข้อความ error ของ Facebook เองก็กำกวมจนชี้ไปผิดทาง

---

## 2. สาเหตุที่แท้จริง (Root Cause)

### สาเหตุหลักที่ 1 — เอา App ID ไปใส่ในช่อง Page ID

`898070703351838` **ไม่ใช่ Page ID แต่เป็น App ID** ของแอป Facebook ที่ผู้ใช้สร้างไว้เอง (แอปชื่อ "POCnews")

หน้า Meta for Developers แสดงเลข ID หลายตัวอยู่ใกล้กัน หน้าตาเหมือนกันหมด (ตัวเลขยาว) และ **คู่มือของเราเองก็ไม่ได้เตือนเรื่องนี้ไว้เลย**

Facebook ตอบว่า *"Object ... does not exist"* ทั้งที่ object นั้นมีอยู่จริง — แค่เป็นคนละชนิด ข้อความนี้จึงชี้นำผิดทางอย่างรุนแรง

### สาเหตุหลักที่ 2 — ใช้ User token แทน Page token

token ที่ Graph API Explorer ให้ตอนกด Generate คือ **User token** ซึ่งโพสลงเพจไม่ได้ ต้องนำไปแลกเป็น Page token ผ่าน `/me/accounts` ก่อน คู่มือขั้นที่ 3 มีขั้นตอนนี้อยู่ แต่ไม่ได้เน้นว่าเป็นขั้นที่**ห้ามข้าม** และไม่มีวิธีตรวจสอบว่าตัวเองถืออะไรอยู่

สาเหตุนี้ถูกบดบังด้วยสาเหตุที่ 1 — ตราบใดที่ Page ID ยังผิด ระบบจะตายที่ code 100 ก่อน ไม่มีทางไปเจอ code 200 ปัญหาสองชั้นจึงโผล่ทีละชั้น ทำให้ดูเหมือน "แก้แล้วพังใหม่"

### สาเหตุร่วมที่ 3 — ผู้วินิจฉัย (ผม) สรุปผิดเพราะเลือกการทดสอบที่แยกสมมติฐานไม่ได้

ตอนตรวจสอบ ID `898070703351838` ผมใช้คำสั่ง:

```
GET /898070703351838?fields=id,name   →   {"id":"898070703351838","name":"POCnews"}
```

เห็นว่า "ตอบกลับมามี id และ name" จึงสรุปว่า **"เป็นเพจจริง ID ถูกต้อง"** แล้วไปโทษว่าเพจนี้ไม่ได้ให้สิทธิ์แอป

**ข้อสรุปนี้ผิด และวิธีทดสอบก็ผิดตั้งแต่ต้น** — เพราะทั้ง App และ Page ต่างก็ตอบ `id` และ `name` เหมือนกัน การทดสอบนี้จึง**ให้ผลเดียวกันไม่ว่าสมมติฐานไหนจะจริง** = ไม่มีค่าในการแยกแยะเลย แต่ผมกลับตีความว่ามันยืนยันสมมติฐานของผม

สมมติฐาน H3 ("ID ที่กรอกไม่ใช่ Page ID") ถูกตัดทิ้งด้วยหลักฐานที่ไม่มีน้ำหนัก ทั้งที่มันคือคำตอบ

การทดสอบที่ถูกต้องคือใช้ฟิลด์ที่**มีเฉพาะในเพจ**:

```
GET /898070703351838?fields=fan_count  →  ERROR: nonexisting field (fan_count)   ← เป็น App
GET /1943605112601214?fields=fan_count →  {"fan_count":0}                        ← เป็น Page
```

**บทเรียน: การทดสอบต้องเลือกตัวที่ให้ผลต่างกันเมื่อสมมติฐานต่างกัน ไม่ใช่แค่ตัวที่ "รันผ่าน"**

### สาเหตุเชิงระบบ

- ระบบยอมรับค่าอะไรก็ได้ลงช่อง Page ID โดยไม่ตรวจสอบ แล้วปล่อยให้ไปพังที่ Facebook
- ไม่มีวิธีตรวจสอบการตั้งค่าโดยไม่ต้องโพสจริง — ผู้ใช้ต้อง "ลองยิงแล้วอ่าน error" เท่านั้น
- error ของ Facebook ถูกส่งต่อให้ผู้ใช้ดิบ ๆ โดยไม่มีการแปลความ

---

## 3. การแก้ไขและการยืนยัน (Resolution)

1. **แลก User token → Page token** ผ่าน `/me/accounts` แล้วบันทึกลง `topics.fbPageToken`
   ยืนยันด้วย `GET /me` → คืน `{"id":"1943605112601214","name":"AutoBot-Maxi"}` = เป็น Page token จริง
   ตรวจกับ `debug_token`: `type: PAGE`, `expires_at: 0` (ไม่หมดอายุ), มี `pages_manage_posts` ครบ
2. **แก้ Page ID** เป็น `1943605112601214` (AutoBot-Maxi) ซึ่งเป็นเพจจริงเพียงเพจเดียวของผู้ใช้
3. **พิสูจน์ว่า `898070703351838` เป็น App ไม่ใช่ Page** ด้วยการทดสอบ `fan_count` (ดูข้อ 2)
   — และแจ้งแก้คำวินิจฉัยที่ผิดของตัวเองให้ผู้ใช้ทราบ
4. **ยืนยันขั้นสุดท้าย:** ผู้ใช้กดโพสเอง → สำเร็จ (`articles.status = posted`, มี `fbPostUrl`)

## 4. สิ่งที่ทำเพื่อไม่ให้เกิดซ้ำ (Preventative Action Items)

### ✅ ทำเสร็จแล้ว

| # | รายการ | รายละเอียด |
|---|---|---|
| 1 | **ปุ่ม "🔌 ทดสอบการเชื่อมต่อ"** | `diagnoseConnection()` ใน `src/lib/facebook.ts` + `POST /api/topics/:id/test-connection` — ตรวจแบบอ่านอย่างเดียว บอกเป็นภาษาไทยว่า "นี่คือ App ID ไม่ใช่ Page ID" / "นี่คือ User token ต้องแลกก่อน" / "Page token ของคนละเพจ" / "token หมดอายุ" ทดสอบครบ 5 สถานการณ์ |
| 2 | **ตรวจรูปแบบ Page ID** | บังคับ `^\d+$` ทั้งตอนโพสและตอนทดสอบ — ตีตกก่อนยิงออกเน็ต |
| 3 | **ปิดช่องโหว่ path injection** | `pageId` จาก DB ถูกต่อเข้า URL ของ Graph API ตรง ๆ (ค่าอย่าง `me/accounts` เปลี่ยน endpoint ได้) — เพิ่ม `encodeURIComponent` + regex ทุกจุด **(เจอระหว่างแก้เคสนี้ ไม่เกี่ยวกับเหตุการณ์)** |
| 4 | **แก้คู่มือ** | `docs/FACEBOOK_SETUP.md` — กล่องเตือน ⛔ "อย่าเอา App ID ใส่ช่อง Page ID", ⛔ "User token ≠ Page token" พร้อมวิธีเช็คด้วย `/me`, และเขียนตาราง troubleshooting ใหม่ให้ code 100 แตกเป็น 3 กรณี |
| 5 | **ทางหนีทีไล่: Manual Post** | ปุ่ม "📋 คัดลอกโพสต์" + "📝 โพสเองแล้ว" — ผู้ใช้ที่ตั้ง token ไม่สำเร็จยังใช้ระบบได้ ไม่ต้องรอแก้ปัญหา Facebook ให้จบก่อน |

### ⬜ ยังไม่ได้ทำ (เรียงตามความสำคัญ)

| # | รายการ | เหตุผล |
|---|---|---|
| 6 | **เขียน automated test** | **โปรเจกต์นี้ยังไม่มี test สักตัว** ทุกอย่างพึ่งการทดสอบด้วยมือ — งานที่ควรทำก่อน deploy: test ของ `diagnoseConnection` (mock การตอบของ Graph API ทั้ง 5 เคส) และของกติกา normalize ใน `src/lib/normalize.ts` |
| 7 | **ตรวจ Page ID ตั้งแต่ตอนบันทึก** | ตอนนี้ตรวจแค่ตอนโพส/ตอนกดทดสอบ ควรเรียก `diagnoseConnection` ตอน PATCH หัวข้อ แล้วเตือนทันทีที่กดบันทึก (แต่ต้องไม่บล็อกการบันทึก เผื่อ Facebook ล่ม) |
| 8 | **บันทึก log ของ error code จาก Facebook** | ตอนนี้ error หายไปกับ response ไม่มีร่องรอยให้ย้อนดู ถ้ามีคนอื่นมาใช้จะวินิจฉัยไม่ได้เลย |
| 9 | **ยืนยันสิทธิ์ `pages_manage_posts`** | ปุ่มทดสอบยืนยันได้แค่ "token เป็นของเพจนี้" — วิธีพิสูจน์สิทธิ์โพสจริงมีทางเดียวคือโพส ทางเลี่ยง: `GET /{pageId}/feed?limit=1` เช็คสิทธิ์อ่านเป็นตัวแทน |
| 10 | **แจ้งเตือนก่อน token หมดอายุ** | token ปัจจุบัน `expires_at: 0` (ไม่หมดอายุ) แต่จะพังเงียบ ๆ ถ้าผู้ใช้เปลี่ยนรหัสผ่าน Facebook หรือถอนสิทธิ์แอป — ควรมี cron เช็คเป็นระยะ |

### 📌 ความรู้ที่ต้องไม่ลืม

- **`?metadata=1` ใช้แยกชนิด object ไม่ได้แล้วใน Graph API v23.0** (ไม่คืน `metadata.type`) — ตรวจสอบแล้วด้วยการยิงจริง วิธีที่ใช้ได้คือดูฟิลด์เฉพาะชนิด เช่น `fan_count`
- **App ID กับ Page ID หน้าตาแยกไม่ออก** และ Facebook คืน `id` + `name` ให้ทั้งคู่
- **code 100 "does not exist" ไม่ได้แปลว่าไม่มีอยู่จริง** — แปลได้ทั้ง "ผิดชนิด" "ไม่มีสิทธิ์" และ "ไม่มีจริง"

## 5. สิ่งที่ทำได้ดี

- ผู้ใช้จับได้เองว่าการเก็บ FB token ไว้ใน env ทำให้ระบบหลายบัญชีใช้ไม่ได้ — แก้เป็น token ต่อหัวข้อก่อนจะเจอปัญหานี้ ทำให้ตอนดีบักไม่ต้องรื้อสถาปัตยกรรมกลางทาง
- การแยกชั้น `FacebookError` เป็น `config` กับ `api` ทำให้ error ตอนตั้งค่าผิดไม่ไปทำเครื่องหมายข่าวเป็น `failed` มั่ว
- ไม่มีโพสต์ผิดพลาดขึ้นเพจจริงเลยตลอดการดีบัก เพราะยึดกฎว่าไม่โพสแทนผู้ใช้โดยไม่ได้รับอนุญาต
